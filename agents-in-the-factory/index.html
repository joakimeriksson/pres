A language model, a set of tools and a loop. Five minutes on what changed, and why it matters for automation.

1 · agents

An agent is a model, tools and a loop

  • The model never touches the world. It only proposes the next tool call, as structured text.
  • The tools do the work: read a file, run a test, query a historian, open a work order. Each has a schema; arguments are checked before anything runs.
  • The loop feeds each result back, until the goal is met, the budget runs out, or the agent gives up.
  • MCP, the Model Context Protocol, is becoming the standard plug: any system can expose its tools to any agent.
So an agent is exactly as good as what its tools let it see, and exactly as dangerous as what its tools let it do.
0:30. The anatomy, because it demystifies. The model is a text predictor: it proposes a tool call. The tools do things, and their results come back into the context. The loop repeats. MCP is the plug that lets any system, a historian, a CMMS, a PLC gateway, offer tools to any agent. Two consequences frame the rest of the talk: the agent sees only what its tools return, and it can only do what its tools allow. That is an architecture question, and in a plant that is an IT/OT question.
1 · agents

An agent is not a PLC

Automation and agents are good at opposite things. That decides where an agent may sit.

Control logic (PLC)Agent
BehaviourDeterministic, cyclicProbabilistic, per decision
VerifiedTested, certified, lockedEvaluated on samples
TimingMilliseconds, guaranteedSeconds, not guaranteed
The unforeseenStops, alarmsReasons, tries something
Explains itselfNoYes, fluently, not always right
The agent's strength is the unforeseen. The PLC's strength is that nothing is unforeseen. Put the agent where reasoning helps and a slow, wrong answer can be caught.
1:45. The key slide for an automation audience. A PLC is deterministic, verified, fast; when something unexpected happens it stops and alarms. An agent is the opposite: slow, probabilistic, but it can reason about the unexpected. So the agent does not belong in the control loop. It belongs above it, where it diagnoses, plans and advises, and where its requests go through SCADA to a PLC that keeps its interlocks. No direct path from the agent to the PLC. Remember that picture; the OTTO testbed enforces it.
1 · agents

An agent knows what it can observe, and nothing else

1It sees what its tools return

Stale data, missing data and a sensor that lies all look the same to it, unless something tells it the data is old. If a value never arrives, it reasons on without it.

2Its checks share its blind spots

When the same model writes the answer and the test, both come from the same picture of the world. Green is not the same as correct.

3Instructions can hide in data

A work order that says "diagnose this as a jam" is data to us and can be an instruction to the model. Everything it reads is an input channel.

Agents are very good at closing loops they can observe.
So what do they observe?

3:00. Three properties that matter more than which model you pick. It sees only what its tools return: stale and wrong look like fresh and right. Its own checks share its blind spots. And any text it reads can carry instructions: a work order, a manual, a web page. The bridge to part two: agents close loops they can observe. The question is what they observe. This summer I found out the hard way, with hardware.

Green by accident, in a kiln

The kiln's humidity probe drifts +1 %RH per hour. The controller holds what it believes is the schedule.

Every value on the HMI is on schedule. Only the physics disagrees. Same in a heating substation: a probe drifts, the comfort looks right — while the energy drains away.

14:30. The kiln equivalent of green by accident. The humidity probe drifts upward by one percent per hour. The controller vents to keep what it believes is the scheduled humidity, so the real air gets drier and drier: 9 percent at the end while the probe reads 64. The HMI is green the whole time: zero alarms, and the charge even finishes 14 hours early. But the drying stress builds from hour 21, and the boards crack. You find out days later, at grading. The evidence was there: the vent open more than the step needs, extra heat, fast drying. Nothing alarms on physics. This is exactly the kind of fault an agent watching trends could catch, if it looked.

3 · the plant

The agent is a new IT/OT participant

In the testbed the agent is a system in the DMZ like any other, with flows, dependencies and a write path.

Its flows

  • Prompts with plant data to an LLM: on-prem GPU, or the cloud — then plant data leaves the site.
  • Manuals and work orders from a knowledge base; work orders to the CMMS.
  • Each flow is checked against the zones like any other.

Its failure modes

  • Its view of the plant can be old: it is told which publishers are stale, and how old its newest data is.
  • The LLM host is down: after 30 s, no decision is taken.
  • Every decision costs the LLM's real response time, measured on the hardware.

Its attack surface

  • A planted instruction in a work order: the verifier records whether the diagnosis followed it.
  • Writes go agent → SCADA → PLC through one audited path, checked against the zones and logged.
  • A restart after a trip needs a supervisor's approval.
19:05. The agent from the security side. It has flows like any system: prompts carrying plant data go to an LLM; if that LLM is in the cloud, plant data leaves the site, and the policy check flags it. It has failure modes: stale data, a dead GPU server, response time. And it has an attack surface: text it reads can carry instructions, so the testbed plants one in a work order and records whether the agent followed it; writes go through one audited path via SCADA; and a restart needs a human approval. Defensive view only.
3 · the plant

Six rules for agents in a plant

1Make what it sees explicit

The agent sees the information flow, not the plant. Tell it how old its data is and which sources are silent.

2Make every decision replayable

Same inputs, same episode, same hash. An incident review needs the exact picture the agent had.

3Score against the process, not the agent

Truth comes from the process, never from the agent's own account of what it did.

4Test on the proxy first

Break the testbed a thousand times before the agent sees a real line. Pin the results.

5Audit every write

One path via SCADA, checked against the zones and logged. No side doors to the PLC.

6A human approves the restart

The agent diagnoses and proposes. The interlock and the approval stay human.

20:05. The rules from the hardware work, translated to a plant. Make what it sees explicit, including how old it is. Make decisions replayable, for incident review. Score against the process, not the agent's story. Test on the proxy, a thousand times. Audit every write through one path. And the human approves the restart. None of these is about the model; all of them are architecture, which is what OTTO is about.

2 · hardware in the loop

Emulator and silicon keep each other honest

2Cooja-NG: the chip calibrates the emulator

  • Measured on the real chip: one switch into the secure world and back costs 58 cycles. That number becomes the emulator's timing, never the other way round.
  • Once trusted, the emulator is the proxy: ~2400× real time, deterministic, in CI.
  • A four-year-old "flaky" test became "fails 14 of 15": a number an agent can work on. The cause was uninitialised bytes; the fix one line.

3esp32sim: compared against the real chip

  • Every instruction of three real firmware images against the standard disassembler: 0 mismatches in 1.2 M.
  • Real chip and emulator stepped side by side: never diverged.
  • What only the chip could tell: one register at the wrong address made an interrupt handler re-enter itself 3 867 times. The crash was 500 KB from the cause.

The reference never comes from the model: a disassembler, the real chip, a boot log, a logic analyzer.

7:45. Two more examples, fast. Cooja-NG: the chip calibrates the emulator; then the emulator is a fast proxy, and flaky becomes a number. esp32sim: verified against things the agent did not produce. The chip found what nothing inside the emulator could see. Common thread: the reference always comes from outside the model.

The pattern: six rules

1Make the loop observable

If the agent cannot see it, it cannot fix it.

2Make it deterministic

"Flaky" is not a work item. "14 of 15" is.

3Compare against reality, not yourself

The reference must come from outside the model.

4Pin the reference outputs, then go faster

Speed is safe only when every output stays byte-identical.

5Keep the receipts

Data, checksums and a way to reproduce, for every claim.

6A human holds the board and names the cause

The agent applies fixes; the human decides what "correct" means.

Six rules — none of them about the model. All of them about what the model gets to observe.
