0:00. One line: this summer, four hardware projects were built with coding agents in the loop. Very different projects; the pattern that made them work is the same. Ten minutes.

The loop a coding agent closes is its own

Coding agents are extremely good at closing loops they can observe.

Left alone, the loop they observe is their own model of the world: the code they wrote, the tests they wrote, the log lines they expected.

Tests written by the same model that wrote the code share its blind spots. Green is not the same as correct.

Hardware does not share the model's blind spots.

Green suites that are green by accident are the failure mode that scares me: the tests pass, the model is happy, and nobody touched a board.
0:15. The claim. Agents close loops. The danger is that the loop they close is entirely inside their own head: code, tests and expectations all come from the same model. Hardware is the one thing in the room that does not share those blind spots. So: how do you put it in the loop, in practice?

Put the chip in the loop, and give the agent eyes

Three roles for hardware in the loop. The four examples use all of them.

1:00. The pattern in one picture. The agent still writes the code, but what it observes now comes from an emulator and from silicon, diffed against each other. Hardware plays three roles: oracle, the board has the last word; calibrator, its measured timings feed the emulator; proxy, the emulator as a fast, repeatable stand-in. Every example is one trip around this loop.

2Cooja-NG: real chip and emulator correct each other

The Contiki-NG network simulator, rewritten to be fast and repeatable, kept honest by the real boards it imitates

The real chip calibrates the emulator

  • On the real board, the chip's own cycle counter says: one switch into the secure world and back (TrustZone) costs 58 cycles.
  • Cooja-NG boots the same firmware and counts 389 switches in, 390 out.
  • The measured number becomes the emulator's timing, never the other way round.

The board finds what the emulator cannot

  • A radio stopped receiving: the driver asked the chip for status so often that incoming packets never got a turn. Only visible with a logic analyzer on the wires.
  • Two negative results written down: the time-slotted radio mode does not work yet on two new boards. Writing is cheap now.

The emulator closes the CI loop

  • 93 / 93 of the project's tests pass on it. Switching CI over is one line; CI downloads a prebuilt binary.
  • ~2400× real time: a 60-second scenario in under 0.1 s.
A four-year-old flaky test: one compiler, 15 runs: the other compiler passes "by luck of stack contents". Cause: uninitialised bytes in a radio setting, hidden since 2022. Fix: one line.
A deterministic simulator turns "flaky" into "14 of 15", and 14 of 15 is something an agent can work on.
2:45. Second example, hardware as calibrator. A cycle count measured on the real board becomes the emulator's timing. The radio bug was only visible on a logic analyzer — no emulator would have shown it. Once the emulator is trustworthy it becomes the proxy: 2400× real time, deterministic, in CI. Which is how a four-year-old flake finally got fixed: 14 of 15 is a number, flaky is not.

Why the cause was 500 KB from the crash

One wrong address in the emulator. The real chip's boot log was the only thing that disagreed.

  1. A timer interrupt arrives. The chip drops what it is doing and runs a small handler. The handler's first act is to flip a hardware switch that says "no more of these until I'm done".
  2. The emulator had that switch at the wrong address. The write landed nowhere. Nothing complained.
  3. So the same interrupt fired again, inside its own handler. Each time, the chip notes where it was on the stack, its scratch pile in memory, and starts over. 3 867 times.
  4. The stack grew down through all of memory and into the program itself. When the chip next ran that part of the program, it was stack rubbish: illegal instruction.

The crash pointed at the handler. The bug was one address in a register model, 500 KB away, and only the real chip's boot log disagreed with the emulator.

5:55 (25 s). In plain words: an interrupt is the chip being tapped on the shoulder. The first thing the handler does is say "don't tap me again until I'm done", by writing a hardware switch. The emulator had that switch at the wrong address, so the write vanished. The chip got tapped again inside the handler, 3 867 times, each one adding to the stack, until the stack had overwritten the program. The crash was in the handler; the bug was one address in the emulator's register map, 500 KB away. Nothing inside the emulator could see it; the real board's boot log could.

Two stories the green tests never told

Two wrongs made a right

  • The emulator's audio output assumed 44.1 kHz; the music player actually asks for 22.05 kHz → music at double tempo…
  • …while the emulator ran at 0.5–0.8× real time. The errors cancelled. Every test stayed green until the pacing was exact.
  • It surfaced the day a speed-up made the emulator run at exactly real time. Bonus, from an oscilloscope on the real board: the vendor's audio driver actually runs at 44 101 Hz.

2× tempo  ×  0.5× speed  ≈  sounds right

Making the emulator faster found a correctness bug. Every green test had passed with both errors in place.

The pattern

1Make the loop observable

What the board prints, what its screen shows, instruction counts, audio fingerprints, cycle counts. If the agent cannot see it, it cannot fix it.

2Make it deterministic

"Flaky" is not a work item. "14 of 15" is.

3Compare against the real chip, not yourself

A standard disassembler, the real chip stepped alongside, a real boot log, one LED at a time. The reference must come from outside the model.

4Pin the reference outputs, then go faster

Speed is safe only when every output stays byte-identical — and going faster is how the cancelling bugs surface.

5Keep the receipts, including the rejections

Data, checksums and a way to reproduce, for every claim; rejected candidates stay, with numbers. "alice": 120 commits, 25 PRs, 5 days, every one with receipts.

6A human holds the board and names the cause

The agent applies fixes; the human decides what "correct" means and what a green test is hiding.

Six rules — none of them about the model. All of them about what the model gets to observe.

8:00. The pattern, six rules. None of them is about the model. They are all about what the model gets to observe, and making sure the golden it is measured against did not come from its own head.

Where the agents stopped

What we saw, again and again

"The agent could apply a fix once we named the cause, but it could not reliably name the cause itself."— Cooja-NG paper, SNCNW 2026
"…often proposed a local workaround ('enlarge the buffer', 'treat as non-fatal') when the correct fix was further up the call stack."— Cooja-NG paper, SNCNW 2026

What worked: a persistent bug ledger — human-named root causes, fed back into the agent's context on every run.

What I actually learned this summer

1The bottleneck moved from writing to observing

Code is cheap now. The scarce work was building the instrument: the screen saved as images, the chip stepped alongside the emulator, the one-LED self-test. Whoever builds the eyes decides what gets fixed.

2Green by accident is the new default failure

The bugs that survive a competent agent are the ones that cancel each other out. They don't show up in tests — they show up when you go faster, or when you diff against silicon.

3Naming the cause is still human work

The agent applied fixes once we named the cause, and reached for local workarounds when we didn't. Verification is automatable. The bug ledger of human-named root causes was the most valuable file in every repo.

The one that scares me What was left for the human in the loop was a cable and a button. Those are the rows we will automate first — and then the same blind spots that give us green-by-accident tests will give us green-by-accident actuation.

The models are super competent. Put the hardware in the loop anyway.

9:20. Three conclusions. One: the bottleneck moved from writing code to building the instrument that observes it. Two: green by accident is the failure mode that survives a competent agent. Three: verification is automatable, naming the cause is not yet; the bug ledger of human-named root causes was the most valuable file in every repo. And the warning: what was left for the human was a cable and a button, and those are the first rows we will automate. The models are super competent. Put the hardware in the loop anyway.
