0:00. One line: this summer, four hardware projects were built with coding agents in the loop. Very different projects; the pattern that made them work is the same. Ten minutes.

The loop a coding agent closes is its own

Coding agents are extremely good at closing loops they can observe.

Left alone, the loop they observe is their own model of the world: the code they wrote, the tests they wrote, the log lines they expected.

Tests written by the same model that wrote the code share its blind spots. Green is not the same as correct.

Hardware does not share the model's blind spots.

Green suites that are green by accident are the failure mode that scares me: the tests pass, the model is happy, and nobody touched a board.
0:15. The claim. Agents close loops. The danger is that the loop they close is entirely inside their own head: code, tests and expectations all come from the same model. Hardware is the one thing in the room that does not share those blind spots. So: how do you put it in the loop, in practice?

Put the chip in the loop, and give the agent eyes

Three roles for hardware in the loop. The four examples use all of them.

1:00. The pattern in one picture. The agent still writes the code, but what it observes now comes from an emulator and from silicon, diffed against each other. Hardware plays three roles: oracle, calibrator, proxy. Every example is one trip around this loop.

2Cooja-NG: silicon and emulator correct each other

The Contiki-NG simulator reimplemented in C, kept honest by the boards it emulates

Silicon calibrates the emulator

  • nRF54L15 DK, DWT CYCCNT over SWD: one TrustZone transition (NS → SG → secure → BXNS) = 58 cycles.
  • Cooja-NG tz-boot on the same image: 389 SG + 390 BXNS.
  • The silicon number sets the emulator's cost model, not the other way round.

Hardware finds what emulation cannot

  • CC1200 sub-GHz: polling starved the RX IRQ on the SPI bus (#3140, #3206). Only visible with a logic analyzer.
  • Two negative results written down: TSCH on nRF54L15 and on Gecko. Writing is cheap now.

The emulator closes the CI loop

  • 93 / 93 upstream tests pass. SIMULATOR=cooja-ng is a one-line switch; CI downloads a binary per tag.
  • ~2400× real time: a 60 s scenario in < 0.1 s.
A four-year-old flake: 21-cooja-rpl-tsch-security, gcc, 15 runs: clang passes "by luck of stack contents". Uninitialised TSCH enhanced-ACK params (#3205), hidden since a 2022 timeout bump. One memset.
A deterministic simulator turns "flaky" into "14 of 15", and 14 of 15 is something an agent can work on.
2:45. Second example, hardware as calibrator. A cycle count measured over SWD on the real nRF54L15 becomes the emulator's cost model. The CC1200 bug was only visible on a logic analyzer — no emulator would have shown it. Once the emulator is trustworthy it becomes the proxy: 2400× real time, deterministic, in CI. Which is how a four-year-old flake finally got fixed: 14 of 15 is a number, flaky is not.

The pattern

1Make the loop observable

Console diffs, PNG frames, instruction counts, WAV hashes, cycle counters. If the agent cannot see it, it cannot fix it.

2Make it deterministic

"Flaky" is not a work item. "14 of 15" is.

3Diff against silicon, not against yourself

objdump, JTAG lock-step, a real boot log, one LED at a time. The golden must come from outside the model.

4Pin goldens, then go faster

Speed is safe only when every output stays byte-identical — and going faster is how the cancelling bugs surface.

5Keep the receipts, including the rejections

JSON + hashes + repro for every claim; rejected candidates stay, with numbers. "alice": 120 commits, 25 PRs, 5 days, every one with receipts.

6A human holds the board and names the cause

The agent applies fixes; the human decides what "correct" means and what a green test is hiding.

Six rules — none of them about the model. All of them about what the model gets to observe.

8:00. The pattern, six rules. None of them is about the model. They are all about what the model gets to observe, and making sure the golden it is measured against did not come from its own head.

Where the agents stopped

What we saw, again and again

"The agent could apply a fix once we named the cause, but it could not reliably name the cause itself."— Cooja-NG paper, SNCNW 2026

What I actually learned this summer

1The bottleneck moved from writing to observing

Code is cheap now. The scarce work was building the instrument: the PNG per frame, the JTAG lock-step, the one-LED self-test. Whoever builds the eyes decides what gets fixed.

2Green by accident is the new default failure

The bugs that survive a competent agent are the ones that cancel each other out. They don't show up in tests — they show up when you go faster, or when you diff against silicon.

3Naming the cause is still human work

The agent applied fixes once we named the cause, and reached for local workarounds when we didn't. Verification is automatable. The bug ledger of human-named root causes was the most valuable file in every repo.

The one that scares me What was left for the human in the loop was a cable and a button. Those are the rows we will automate first — and then the same blind spots that give us green-by-accident tests will give us green-by-accident actuation.

The models are super competent. Put the hardware in the loop anyway.

9:20. Three conclusions. One: the bottleneck moved from writing code to building the instrument that observes it. Two: green by accident is the failure mode that survives a competent agent. Three: verification is automatable, naming the cause is not yet; the bug ledger of human-named root causes was the most valuable file in every repo. And the warning: what was left for the human was a cable and a button, and those are the first rows we will automate. The models are super competent. Put the hardware in the loop anyway.
